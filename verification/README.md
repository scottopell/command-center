# CommandCenter verification

Fresh results for this repository are recorded after running the local checks. Code and requirement mappings are in [requirements.json](requirements.json); the behavioral acceptance journeys are in [the specification checks](specs/acceptance.md).

- `npm run check`: TypeScript, function source guards, backend, CLI, persistence and HOST fixtures.
- `npm run check:specs`: requirement identity, status/link validation and Allium analysis.
- `npm run build`: UI and worker bundles plus the native app.
- `npm run test:native`: actual WebKit, isolated backend stores, lifecycle/input/cancellation checks, and repeated disposal samples.

The foreground-only 500 ms transition contract ends at the framework's animation-frame and queued-task checkpoint, independently of input ownership, buffer length and application-data reads. Background interruption permanently excludes an undetected measurement; it neither pauses the raw clock nor removes an existing straggler. It is not a compositor-presentation measurement. The native display-flush benchmark is a separate historical metric; it does not prove transition readiness or promise fixed RSS, garbage collection timing or performance under arbitrary OS stalls. Cold application startup is outside the running-app transition contract.

See [the current result summary](summary.json), [static and backend results](check-results.txt), [native results](native-results.txt), [native samples](native-benchmark.json). No live ticket payloads or client credentials are stored here.


Retained navigation adds actual WebKit Back, loading/error/authority and primary viewport checks. Query tests exercise the real TanStack client with inactive-cache clock advancement, superseded reads, unknown attempts and writes completing after pop/disposal. Response-cap tests use large fixture records and verify that an uncertain reply does not duplicate a committed comment. Acceptance obligations remain distinct from executed evidence; fixture repetition and serialized size indicators do not constitute heap-snapshot analysis.

Selection and sibling coverage uses private clipboard writers and a unique native pasteboard, leaving the general clipboard untouched during automated tests. Actual WebKit pointer selection, native Select All action routing, editable/programmatic exclusions, failure/size limits, stable collection membership, fresh sibling reads, replacement depth and keyboard repeat/editable behavior are exercised. No owner write API or canonical storage change is part of this feature.

Runtime-pack coverage builds the included NOTES fixture with the packaged SDK/compiler, installs and updates it, removes the source folder, checks storage identity isolation, rejects collisions and stale revisions, injects a startup failure, and drains a disconnected caller's admitted write. Native tests exercise Apply & Relaunch, retained command focus, and browsing a forced straggler through STRAG. Detector unit tests use an injected monotonic clock; no exact pixel-presentation assertion is claimed. Test stores and collectors are isolated from the operator's records.

The [pack management UI checks](pack-management.json) separately cover its compact, top-aligned layout, installed function names, state-specific actions, stable polling, and request/error recovery. Five UI tests and the three existing pack integration tests pass; fixture views are rendered for visual inspection. This focused run does not replace the recorded full-suite results.

The [compact shell checks](compact-shell.json) cover all 43 functional native cases: function toolbar launches, overflow, current-function highlighting, catalog refresh, inline Back/sibling controls, input handoff, DRQS and selection. This final UI run excludes the long retention soak; its prior pass and later test-host interruption are recorded separately. DRQS submission waits for the enabled action, independently of screen readiness; native pointer-selection fixtures activate their own window.

The historical [minification comparison](minification-benchmark.json) uses identical production `SLOW 0` sources in fresh WebViews, alternating build variants. JavaScript shrank from 1,586,739 to 731,405 bytes (54%); across 30 measured launches per variant, median readiness was 183.1 versus 177.5 ms and p95 was 188.3 versus 182.8 ms. Every view in this run was hidden and used the former 100 ms readiness fallback. These are modest startup gains in an occluded test environment, not isolated parsing timings or evidence of foreground presentation performance. The current `npm run benchmark:bundles` requires foreground frame checkpoints and cannot reproduce that retired readiness path. Raw historical samples remain for reference. The source/backend suite passed all 34 cases, including resolving a minified bundle location back to its original TSX through the linked source map. The native functional run passed 42 cases with the opt-in comparison skipped; the long retention soak and pointer-selection test were excluded. The packaged service/CLI smoke also passed.

The [foreground SLO checks](foreground-slo.json) cover permanent exclusion, preserved detected stragglers, native visibility notification wiring, unchanged raw elapsed timing, history denominators/maxima and a real SDK checkpoint held beyond 250 ms by a controlled frame scheduler. All seven focused native cases passed. The full selected native run passed 18 cases and skipped 31 (including the opt-in benchmark); its test host could not obtain foreground visibility. The long retention soak was not selected. No hidden-window rendering pass is claimed. Source/backend tests, build, packaged service/CLI smoke and all seven specification models passed. Live checks in the rebuilt app recorded an eligible `SLOW 0` frame checkpoint and an excluded background launch, and STRAG displayed the separate eligible/excluded counts. A foreground 30-sample performance comparison has not been rerun.

The [host runtime checks](host-runtime.json) cover same-epoch SDK adoption with unchanged installed function artifacts, immutable runtime generations for open WebKit documents, current-source compatibility checks, and epoch rejection before worker loading with saved data retained. The local full verification passed 36 source/backend cases and 23 native cases; 33 native cases were skipped, including foreground tests whose window could not become visible. Three new module-loading cases ran in actual WebKit independently of foreground readiness. No new startup benchmark or pixel-presentation result is claimed.

The [runtime cache checks](runtime-cache.json) cover OS-managed shared leases across selected SDK values and WebKit documents, final-owner cleanup, a separate native lease-owning process killed without cleanup, abandoned staging/trash, filesystem confinement and retry after failure. Eight focused native cases pass, including a fresh module request from an old WebView after a sweep. Runtime cache reclamation supersedes the deferred-cleanup limitation in the earlier host-runtime snapshot.

The [fresh live transition measurements](transition-benchmark.json) use the current host runtime in the actual CommandCenter app on an Apple M5 Pro (18 logical processors, 64 GiB, macOS 26.6.2). Native accessibility input submits SLOW 0; the production STRAG recorder supplies elapsed times and continuous foreground eligibility. The first function launch after app restart took 212.3 ms. Thirty repeated launches had a 100.8 ms median, 113.4 ms p95 and 114.2 ms maximum; none of the 31 exceeded 500 ms. Every sample completed at the real frame/queued-task checkpoint, with nominal thermal state and no worker operations. Native app startup and cleared OS/WebKit caches were not measured; the single first-use sample is not a cold-start distribution. These endpoint and visibility conditions differ from the historical minification experiment, so its timings are not a comparable speedup baseline.
